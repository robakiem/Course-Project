## ВСТУП

### Актуальність проблеми
Сучасні логістичні системи обробляють величезні обсяги даних у реальному часі. Традиційні централізовані архітектури стають "вузьким місцем" при одночасному оновленні GPS-координат тисяч кур'єрів. Проблема класифікується як **Big Data Challenge** у контексті IoT-даних.

### Об'єкт дослідження
Процеси обробки високоінтенсивних потоків гео-даних у логістичних системах.

### Предмет дослідження
Порівняння архітектур централізованого та розподіленого сховища даних для систем моніторингу в реальному часі.

### Мета роботи
Розробити та реалізувати масштабовану веб-систему моніторингу логістичних потоків, що демонструє переваги розподіленого зберігання даних у контексті latency, availability та scalability.

### Завдання роботи
1. **Аналітичні:** Дослідити та порівняти архітектури даних (ACID vs BASE, CAP-теорема)
2. **Проектні:** Розробити ER-діаграму та схему географічного шардингу
3. **Реалізаційні:** Розробити Web API з логікою розподіленого маршрутизування запитів
4. **Експериментальні:** Провести тестування масштабованості та відмовостійкості
5. **Документаційні:** Підготувати демонстраційні матеріали та аналітичні висновки

### Новизна рішення
- **Географічний шардинг:** Дані розташовуються на регіональних вузлах для зниження latency
- **Edge-агрегація:** Локальні вузли обробляють детальну телеметрію, а у глобальну БД передаються лише агреговані звіти
- **Демонстрація CAP-теореми:** Реалізація практичного вибору між послідовністю та доступністю

## РОЗДІЛ 1: ТЕОРЕТИЧНІ ОСНОВИ РОЗПОДІЛЕНИХ СИСТЕМ

### 1.1. Концепція розподіленого зберігання даних
#### 1.1.1 Централізована архітектура (Monolithic Database)
- **Описання:** Єдина централізована база даних для всіх операцій
- **Переваги:**
  - Простота управління ACID-гарантіями
  - Легкість синхронізації даних
  - Стандартні інструменти та процеси
- **Недоліки:**
  - Single point of failure
  - Обмежена масштабованість горизонтально
  - High latency при великих географічних відстанях
  - Network bottleneck при високій інтенсивності запитів

#### 1.1.2 Розподілена архітектура (Distributed Database)
- **Описання:** Дані розташуються на кількох географічно розташованих вузлах
- **Архітектури:**
  - **Горизонтальний шардинг:** Рядки розподіляються по вузлам
  - **Вертикальний шардинг:** Колони розподіляються по вузлам
  - **Географічний шардинг:** Дані розподіляються за регіонами
- **Переваги:**
  - Висока доступність (High Availability)
  - Низька latency (локальні операції)
  - Горизонтальна масштабованість
  - Resilience до відмов окремих вузлів
- **Недоліки:**
  - Складність синхронізації
  - Можливість inconsistency в даних
  - Необхідність розподіленої трансакційної логіки

### 1.2. CAP-теорема (Brewer's Theorem)
#### Визначення
У розподіленій системі можна гарантувати максимум **два** з трьох властивостей:
- **C (Consistency):** Усі клієнти бачать однакові дані в один момент часу
- **A (Availability):** Система завжди доступна для читання/запису
- **P (Partition tolerance):** Система продовжує працювати при розривах мережі

#### Застосування в Smart-Post:
| Сценарій | Выбор | Обґрунтування |
|----------|-------|---------------|
| Оновлення координат кур'єра | **A + P (BASE)** | Координати можуть бути трохи застарілими, але система повинна бути завжди доступна |
| Фіскальна операція платежу | **C + A (ACID)** | Гроші потребують абсолютної точності |
| Статус посилки | **C + P** | На розривах мережі система чекає консистентності |

### 1.3. ACID vs BASE
#### ACID (Atomicity, Consistency, Isolation, Durability)
- Необхідна для фінансових операцій та критичних даних
- Гарантує транзакційну цілісність
- Вищі видатки на координацію

#### BASE (Basically Available, Soft state, Eventual consistency)
- Оптимальна для Big Data та IoT
- Допускає тимчасову inconsistency
- Вищий throughput та низька latency
- Застосовується для телеметрії та координат

### 1.4. Стратегії шардингу
#### 1.4.1 Hash-Sharding
```
Формула: shard_id = hash(key) % number_of_shards
```
- **Переваги:** Рівномірний розподіл навіть для впорядкованих даних
- **Недоліки:** Складна переміграція при добавленні нових шардів
- **Применение:** Коли важна рівномірність розподілу

#### 1.4.2 Range-Sharding
```
Формула: shard_id = findRange(key_value)
```
- **Переваги:** Легко робити запити по діапазонам
- **Недоліки:** Можлива неоднорідність розподілу
- **Применение:** Географічна розподіл (по регіонам, кодам міст тощо)

#### 1.4.3 Directory-Based Sharding
- **Описання:** Явна таблиця відповідності ключ -> шард
- **Переваги:** Найбільш гнучка, легко переміграти
- **Недоліки:** Додаткова точка контролю (Directory Service)
- **Применение:** Коли потребується точна контроль розподілу

#### 1.4.4 Вибір для Smart-Post
**Range-Sharding по географічних регіонах:**
- Регіон 1 (Київ, Харків): Шард 1
- Регіон 2 (Львів, Одеса): Шард 2
- Регіон 3 (Інші міста): Шард 3

### 1.5. Паттерни архітектури

#### 1.5.1 Repository Pattern
```csharp
public interface IShipmentRepository
{
    Task SaveShipmentAsync(Shipment shipment);
    Task<Shipment> GetShipmentAsync(string trackNumber);
    Task UpdateShipmentStatusAsync(Guid id, ShipmentStatus status);
}
```
**Мета:** Абстрагування доступу до даних від бізнес-логіки
**Переваги:** Легкість тестування, портативність БД

#### 1.5.2 Strategy Pattern для шардингу
```csharp
public interface IShardingStrategy
{
    int GetShardId(string key);
}
```
**Мета:** Дозволяє змінювати стратегію шардингу без змін кодаLetter
**Применение:** Hash-Sharding, Range-Sharding, Directory-Sharding

#### 1.5.3 Circuit Breaker Pattern
**Мета:** Запобігти cascading failures при недоступності одного шарду
**Реалізація в Smart-Post:**
- Якщо шард не відповідає, система повертає cached дані або помилку з retry logic
- Монітор перевіряє статус шарду кожні 10 секунд
- При відновленні шард повертається в пул

- **Node:** Вузол розподіленої системи

- **Courier:** Кур'єр із GPS

- Розподілена система показує 3x нижчу latency для географічно розподілених клієнтів
